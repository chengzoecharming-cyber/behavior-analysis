## 一、书中在说什么

### 1. 在线系统 vs 离线系统（不是"联网/断网"）

- **在线系统（online）**：请求-响应（request-response）——你问，它马上答。核心指标：**响应时间（response time / latency）**。
- **批处理/离线系统（batch / offline）**：一次作业（job）读一大批输入、算一阵子、产一大批输出，通常周期性调度。核心指标：**吞吐量（throughput）**。
- 区别在"是否立即响应请求"，不在定不定时。

### 2. 本章核心：批处理输出 = 每次从头生成的派生数据

批处理作业的特点：**输入只读、输出每次全量重新生成、不原地修改数据**。因此输出天然是派生数据（derived data），带来三个超能力：

- **容忍人为失误（human fault tolerance）**：代码 bug 算错输出 → 回滚代码、重跑作业即可修复。读写事务的数据库（原地 UPDATE/DELETE）没有这个特性——坏数据写进去，回滚代码救不回来。
- **最小化不可逆性（minimize irreversibility）**：做错了能重来，开发敢放手迭代。
- **同一输入可喂多个作业**：包括**监控作业**——拿同一批数据验证输出是否符合预期。

### 3. MapReduce 与拆分-并行-归并

处理大数据的经典套路：**拆分（split）→ 并行（parallel）→ 归并（merge/reduce）**。map 逐条提取键值，reduce 按键归并。源自 Google 2004 年论文，今天演化为 Spark、Flink、云数据仓库。小数据量用不到框架，但思想通用。

相关术语辨析：

- **并行（parallelism）**：多份同时算、互不干扰，讲加速；**数据并行（data parallelism）**：同一套逻辑作用于不同数据分片。
- **并发（concurrency）**：多件事交替推进、可能互抢资源，讲协调（第 8 章的竞态由此而来）。

### 4. 工作流（workflow / DAG，有向无环图）

真实批处理是一串作业：A 的输出是 B 的输入。**依赖关系必须显式表达**（Airflow 这类工作流调度器干的就是这件事），不能靠"时间上应该来得及"的默契。

## 二、项目对照

| 概念 | 本项目 |
|---|---|
| 在线系统 | 前端页面、控制台 API |
| 批处理作业 | 钉钉同步（每 3 小时）、报告生成（日/周/月）、`recomputeDerivedDataForVisits` |
| 输出 = 从头生成的派生数据 | `routes`、`stops`、`risk_summary_cache`、报告——全部是"删掉重算"模式 |
| 输入只读、原样留存 | `raw_approvals` 保存钉钉原始 JSON（寿司原则） |
| 监控作业 | 同步对账（`syncCheckService.ts` 集合差）、数据质量断言（`dataQuality/assertions.ts`）、告警与心跳 |
| 工作流依赖 | 同步 → 归一化 → 派生重算 → 报告 |
| 调度器（scheduler） | `backend/src/services/scheduler.ts` |
| 数据分层（Medallion Architecture，奖牌分层） | Bronze（`raw_*`）→ Silver（`visits`）→ Gold（`routes`/`stops`/缓存/报告），即 RAW→NORMALIZED→DERIVED |

**本项目 ≈ 丐版大数据平台**：ETL 连接器、数据分层、调度器、物化视图、质量断言、对账监控、告警心跳，零件与大厂数据平台同构，只是规模小。

## 三、两对正交概念（本章最重要的认知地图）

「在线/离线」和「现算/物化」是两个独立维度：

| | 现算（compute on read，相当于数据库视图 view） | 物化（materialize，相当于物化视图 materialized view） |
|---|---|---|
| **online**（请求驱动） | 控制台里程页 | 决策页风险摘要（读缓存） |
| **offline**（定时作业） | —（离线作业的意义就是产出产物） | 日报、routes、stops、风险缓存 |

要点：

- 现算 vs 物化的区别**不在加工链路长短**，在于**结果是否存下来、什么时候算**。现算 = 读时算、算完就扔；物化 = 写时算、读时直接取。
- **选择规则**：算得起 + 要新鲜 → 现算；算着贵 + 能忍旧 → 物化。
- offline 生产物化视图；online 决定读视图还是读物化视图。
- 物化数据"旧了"由**读前自检**发现（派生时间 vs 事实源最新入库时间）；现算不存在"旧"的问题。
- 「丢了就丢了」只对**可重建**的派生数据成立；事实源（visits/raw）丢了就真丢了——必须备份。

## 四、我们踩过的坑（2026-08-03 排查对照）

1. **工作流依赖没声明**：报告作业依赖同步作业完成，但调度器没表达这个依赖，启动时并发抢跑 → 报告读空输入。修复 = 代码里显式串行（手写迷你 Airflow）。
2. **浪费了派生数据的可重建性**：routes 重算"失败即丢数据"、缓存错误永久固化——亲手废掉了批处理最大的优点。修复后（事务化、失败保留旧数据、新鲜度校验）恢复"可重算"超能力。
3. **监控作业缺席**：对账/告警/心跳是跑在同一输入上的监控作业，它们静默时整条 pipeline 是瞎的。

## 五、设计新功能时的检查点

1. 新作业是 online 还是批处理？（决定优化响应时间还是吞吐量）
2. 输出是派生数据吗？是 → 输入必须原样保留，输出必须支持从头重算（不原地改、可删可重建）。
3. 它在工作流哪个位置？上游依赖谁？依赖写进代码了吗？
4. 配了监控作业吗（对账/告警/心跳）？

## 练习题（附参考答案要点）

1. 为什么清理重复 visits 后能靠重算修复衍生数据？——派生数据每次从头生成，输入（visits）修好后重算即得正确输出，无需手工修数据。
2. 启动竞态在工作流概念里是什么问题？——DAG 的依赖边缺失：报告作业依赖同步作业，但调度器未声明，导致并发执行。
3. online/offline 各一例 + 性能指标：控制台页面（online，响应时间）；日报生成（批处理，吞吐量）。

## 统计补给站（Math Corner）

- **吞吐量（throughput）**：单位时间处理的数据量。批处理的第一指标。估算直觉：`总量 ÷ 可用时间`——40 人 × 5 段 × 高德 0.5s/段 ≈ 100 秒，所以同步后重算几分钟内跑完是正常量级。
- **读放大（read amplification）/ 写放大（write amplification）**：一次逻辑操作实际触发多少次物理 IO。物化视图 = 用写放大换读性能；现算 = 零写放大但读时付全价。
- **全量重算 vs 增量计算**：数据量小全量最省心；数据大了只重算"变化的分区"（本项目的脏组合检测 = user+date 分区级增量）。

# 第 2 章精读（第二版）：定义非功能性需求

> 版本说明：本文基于 **DDIA 第二版（Early Release）** 第 2 章「定义非功能性需求」（Defining Non-Functional Requirements）。
> 本章涵盖了第一版第 1 章的主题（可靠性、可伸缩性、可维护性），并以 Twitter 时间线案例贯穿。
> 在线阅读：<https://ddia.vonng.com/ch2/>

## 一、书中在说什么

### 0. 开场框架：需求清单天生少一半

- **功能性需求（Functional Requirements）**：要哪些页面、按钮、每个操作完成什么——需求清单上永远写着的部分。
- **非功能性需求（NFR, Non-Functional Requirements）**：要快、要可靠、要安全、要好维护——看起来像"常识"，**没人写，但同等重要**。一个慢得受不了、天天出错的应用几乎等于不存在。

第 2 章教你把 NFR 说清楚、变成可衡量的要求：**性能（performance）、可靠性（reliability）、可伸缩性（scalability）、可维护性（maintainability）**。

> **NFR 的正确写法 = 可衡量的阈值 + 超标时的动作**。例如「每天 9:30 前日报必须送达，未送达即告警」。判断标准：能不能拿它去验收。

### 1. 案例研究：Twitter 首页时间线

实现「首页时间线（home timeline）」：展示你关注的人的最新帖子（每天 5 亿条）。

- **方案一：现算（compute on read）**。打开首页时实时查「我关注的 200 人最近发了什么」。1000 万在线用户轮询 → 数据库每秒约 4 亿次查询，扛不住。
- **方案二：物化（materialize，预计算）**。为每个用户提前维护好时间线：谁发帖就「投递」到所有追随者的时间线——平均每人 200 追随者，这个放大倍数叫**扇出（fan-out）**。读取从缓存直接返回，每秒写 100 万次 vs 每秒查 4 亿次。
- 边界情况：名人几千万追随者（扇出爆炸）→ 名人帖单独存、读取时合并；关注太多 → 采样丢弃。

核心权衡：**「读的时候算」还是「写的时候算」**——现算省写入但读慢；物化省读取但写入贵，且要维护一份**会过期的副本**。物化时间线就是一种**物化视图（materialized view）**。

### 2. 描述性能

- **响应时间（response time / latency）**：一个请求多久回来。
- **吞吐量（throughput）**：每秒处理多少请求/数据量。
- 两者通过**排队（queueing）**关联：负载逼近系统上限时，排队延迟（甚至拒绝）急剧上升。

### 3. 可靠性与容错（reliability & fault-tolerance）

- **故障（fault）≠ 失效（failure）**：部件出问题 ≠ 系统停摆。可靠性 = fault 不扩散成 failure，即**容错（fault-tolerance）**。
- 三类 fault：**硬件（hardware）**——磁盘等，量大必坏；**软件（software）**——潜伏多年、特定条件才爆发的 bug，比硬件 fault 危险得多；**人为（human）**——误操作、配置错误，大型事故的首要原因。
- 对策方向：硬件靠冗余（redundancy）；软件靠"假设一定会错"的设计（隔离、资源上限、快速失败、监控）；人为靠减少犯错机会 + 可回滚。

### 4. 可伸缩性与可维护性

- **可伸缩性（scalability）**：负载增长时通过增加资源保持性能。
- **可维护性（maintainability）** 三子目标：**可操作性（operability）**——出问题看得见修得快；**简单性（simplicity）**——控制隐式复杂度；**可演化性（evolvability）**——需求变了改得动。

## 二、项目对照

| 概念 | 本项目 |
|---|---|
| 没写进需求清单的 NFR | 需求里有「生成日报」，没写过「同步断了要告警」「派生数据旧了要能发现」——本次事故的 bug 全是清单外的 |
| 物化视图 | `risk_summary_cache`、每日预生成的日/周/月报 |
| 现算 vs 物化并存 | 控制台页面 = 现算（打开时触发重算）；日报/缓存 = 物化（提前算好） |
| 扇出（fan-out） | 一次同步 → 触发 40 人 × N 天的 routes/stops/缓存重算；一次报告生成 → 40 份钉钉文档 + 群消息 |
| 吞吐量与排队 | 高德 API：串行重算稳但慢；`Promise.all` 全员并行追吞吐 → 触发限流（排队的极端形式：拒绝）→ 批量失败丢 routes |
| 软件 fault：潜伏型 bug | 月报 `setTimeout` 溢出——每月 2 日后才触发 |
| 人为 fault | 设计漏项：日志没配轮转——不是代码错，是设计时没人想到 |

## 三、我们踩过的坑（2026-08-03 事故对照）

1. **把物化视图当成不需要维护的东西**：缓存/日报是"会过期的副本"，其维护机制（何时重算、过期谁发现）是设计的一部分。此前只有"算"和"存"，没有"过期发现"——修复后补上了新鲜度校验。
2. **追吞吐触发排队崩溃**：并行打高德超过限流 → 批量失败 → 批量丢 routes。书里的"负载-响应时间"曲线在我们这是"负载-失败率"曲线。
3. **NFR 没有验收标准**：「日报数据要和线上一致」从未被写下，于是它悄悄坏了很久，直到肉眼发现 0。

## 四、设计新功能时的检查点

1. 有没有同时写下**非功能性需求**？（多快算快？多久没跑算异常？数据旧到什么程度算错？——每条都要可验收）
2. 这里用**现算还是物化**？物化的话：过期了谁发现、怎么重算？
3. 这个操作的**扇出**多大？一次触发放大成多少次下游调用？下游扛得住吗？
4. 它坏了（fault）会不会拖死别的部件？有没有资源上限与隔离？

## 练习题（附参考答案要点）

1. 「打开控制台看轨迹」= 现算（放弃写入侧成本，换来永远新鲜）；「每天 9 点日报」= 物化（放弃实时性，换来确定性与可分发）。
2. 8/2 日报里程为 0：物化视图（报告引用的 routes）缺少"过期发现与重算"的维护机制，修复依赖了一个自己控制不了的偶然路径（人工打开页面触发重算）。
3. 可衡量的 NFR 示例：「每天 9:30 前日报必须送达群里，未送达即告警」；「日报里程与生成时刻线上一致，偏差为 0」；「同步断供超 12 小时触发告警」。

## 统计补给站（Math Corner）

本章涉及的最常见统计概念：

- **平均值（mean / average）**：所有值加起来除以个数。容易被极端值带偏——9 个请求 50ms、1 个请求 5s，平均 545ms，但绝大多数用户体感是 50ms。
- **中位数（median）= p50**：排好序取中间那个。一半请求比它快，一半比它慢。
- **分位数（percentile）**：p95/p99 表示 95%/99% 的请求比这个值快。**看性能为什么要看 p99 而不是平均值**：平均值掩盖长尾（long tail），而长尾恰好是用户体验最差的那部分人。以后看到监控里的 p50/p95/p99，就知道是在看"多数人多快 / 近乎所有人多快"。
- **扇出的乘法直觉**：每条帖子 × 200 追随者 = 写放大 200 倍。看到「一次操作触发 N 次下游操作」，先心算 N × 频率，就知道下游压力。
- 相关英文：percentile（分位数）、median（中位数）、mean（平均值）、tail latency（长尾延迟）、load（负载）。

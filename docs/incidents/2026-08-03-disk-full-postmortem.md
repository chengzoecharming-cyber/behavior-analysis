# 2026-08-03 磁盘写满导致数据库崩溃事故复盘

> 状态：已解决并全部上线。相关提交：`dda505a`、`bbe1368`、`d91b554`、`683cf0e`、`d5e21e1`。

## 事故现象

- 钉钉群未收到周报/日报；
- 线上系统登录报错：`钉钉登录失败: the database system is in recovery mode`。

## 根因链（五个环节环环相扣）

1. **scheduler 月报调度 `setTimeout` 溢出**：月报间隔约 30 天（2.5e9 ms），超过 Node `setTimeout` 的 32 位上限（约 24.8 天），被截断为 1ms 立即执行，形成「立即执行 → 重新调度 → 又溢出」的无限重试死循环（`scheduler.ts`）。
2. **死循环刷爆容器日志**：每秒几十行日志，约 2 天写了 **39GB**。Docker json-file 日志驱动默认不轮转。
3. **磁盘写满**：49G 系统盘 100% 占满。
4. **Postgres PANIC**：凌晨 2:00（风险摘要任务时段）checkpoint 无法写盘（`No space left on device`），数据库崩溃。
5. **恢复死锁**：崩溃恢复（WAL replay）本身也需要磁盘空间，空间为 0 → 永远无法完成恢复 → 所有连接报 `the database system is in recovery mode`。

次日凌晨 9:00 的日报任务因此失败；服务重启后「同步补跑」与「报告补跑」**并发**启动，报告读到尚未同步的数据，导致补发的日报里程全 0。

## 处置过程

1. 截断 39GB 后端容器日志，磁盘从 100% 降至 22%；
2. 重启 Postgres 完成崩溃恢复，重启后端，服务恢复；
3. 补发缺失的日报/周报群汇总消息；
4. 随后重新生成了 8/1、8/2 两日的日报（旧报告里程错误，已删除重发）。

## 修复措施（三批，均已上线）

### 直接根因

- `safeSetTimeout`：超过 24.8 天的延迟分段调度，杜绝溢出死循环（`scheduler.ts`）；
- 所有容器配置日志轮转（json-file `max-size: 100m, max-file: 3`，见 `docker-compose.yml` / `docker-compose.ghcr.yml`）——**39GB 日志不会再出现**；
- 修复每月 1 日 9:00 后重启服务会立即重复触发月报。

### 报告与同步时序

- 报告生成前 `ensureFreshRoutes`：只重算「同组 ≥2 条签到但 routes 缺失/过期」的脏组合，保证报告里程与线上一致（此前报告被动读 routes 表，长期与线上漂移）；
- 启动时「同步补跑」与「报告补跑」由并发改为串行，报告不再读到半成品数据。

### 同步链路结构性加固（深度排查后）

- 写入侧：`visits` 部分唯一索引 `(approval_id, user_id, sequence)` + `ON CONFLICT` + 批内去重 + raw/visits 同事务；`syncApprovals` 进程内串行；线上 9 组存量重复已清理；
- 计算侧：stops 纳入自动计算（此前仅人工打开控制台才生成）；routes 重算事务化、高德失败的段保留旧数据、同 user+date 互斥；风险缓存增加新鲜度校验（补卡入库即失效重算，不再永久固化）；
- 告警侧：发送失败不标记已发送（下轮重发）、同步失败也执行告警检查、昨日零同步日志按异常告警、正常日发心跳摘要、手动同步触发告警检查；
- 对账：`missing_count` 由计数差改为真实集合差，hash 两端统一为 approval_id 口径（此前是永不相等的死数据）；
- 清理：废弃「停留过长」规则与全部「停留分钟」展示字段（业务确认弃用）。

## 后续观察项

- 每天 9:00 钉钉群应收到昨日同步健康心跳摘要——**收到 = 同步与告警通道正常，收不到 = 需要排查**；
- 日报里程应与线上数字一致（快照口径：报告反映生成时刻的数据，之后的补卡仍会使线上漂移，属预期）。

## 经验教训

1. **定时任务长延迟必须考虑 setTimeout 上限**，超过 24.8 天要分段调度；
2. **容器日志必须配置轮转**，这是 Docker 部署的默认动作，不能依赖应用「不会刷日志」；
3. **「靠时序保证正确」不如「读的时候自己校验补齐」**：本次多数数据不一致都源于隐式时序假设（同步异步重算、报告被动读表、catchup 并发）。改造方向是让每个读取方在使用前自检数据新鲜度（ensureFreshRoutes、风险缓存新鲜度校验），链路才具备自愈能力；
4. **告警链路本身也要可观测**：发送失败不能静默吞掉；「没有日志」和「一切正常」必须区分开（心跳机制）。

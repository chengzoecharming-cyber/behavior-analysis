# PRD-006 客户同步与生命周期经营

> 状态：🔵 进行中（需求评估）｜ 创建：2026-10-19 ｜ 归属：客户侧数据闭环
> 关系：本需求是 **OA 订单执行接入的上游**；先有客户同步与客户身份/生命周期，再有订单接入与成交判断。
> 原则：不预设只做轻量映射，不排除客户分析、客户管理或其他客户域能力；先完整评估价值，再决定实施边界。

## 一、背景

当前系统以销售外勤数据为主体，已有拜访轨迹、异常、风险、客户分析等能力；CRM 数据目前通过手工 Excel 快照导入，订单执行数据仍停留在钉钉 OA 中。三者尚未形成完整链路：

```text
客户同步（客户是谁）
  → CRM 过程（如何推进、阶段如何变化）
  → OA 订单（是否成交、成交主体是谁）
  ↺ 销售外勤（过程中实际拜访/陪同/行动）
```

2026-10-19 已验证两张订单执行 OA 均可读取实例详情：

| OA 模板 | process_code | 已确认的关键事实 |
|---|---|---|
| 订单执行 | `PROC-C7E24D17-88EB-4AE1-BA2E-1B96B45B7AC0` | 客户名称、签约主体、合同编号、需求产品明细、交付信息等可读 |
| 【代理商】订单执行 | `PROC-EB1872CE-B31A-4228-8D79-E839808959A7` | 「客户名称」是终端客户，「要发货的代理商名称」是代理商，两者必须分开建模 |

同时验证到：OA 的「客户名称」关联字段内嵌 CRM 客户 `instanceId`，可直接用于客户关联；本地 CRM 快照是手工导出的旧数据，部分 OA 中已存在的新客户尚未进入本地快照。

负责人已确认：探迹 CRM 的接口需要额外费用，当前 **CRM 只能手动同步**。这不是本 PRD 要掩盖的问题，而是必须围绕它设计同步节奏、快照差异和数据新鲜度提示的现实约束。

## 二、需求定位

这不是“为了接订单顺手补一个客户映射表”，而是一个独立的客户域需求。它同时产生两类价值：

1. **OA × CRM 整合后的自身价值**：看清客户从创建、跟进到成交的完整生命周期，以及 CRM 过程状态与 OA 实际成交是否一致。
2. **OA × CRM × 销售外勤整合后的价值**：解释过去（什么动作带来了推进或成交），并指导未来（哪些客户需要拜访、跟进、挽回或通知负责人）。

客户的完整生命周期与成交事实不应只依赖 CRM 阶段：CRM 阶段仍描述过程，但 **OA 订单执行单才是成交事实与成交主体的准绳**。两者打通后，CRM 阶段的重要性会下降，系统可以直接根据 OA 判断“是否真的成交”。

## 三、目标

### 3.1 客户完整生命周期

建立每个客户可回看的时间线，至少能表达：

- 客户创建、进入 CRM、分配负责人；
- 跟进阶段及状态变化、各节点停留时长；
- 跟进记录与跟进频次；
- 外勤拜访、陪同拜访及最近实地触达；
- 订单执行发起、合同确认、ERP/发货/交付等 OA 节点；
- 退回公海、重新分配、起死回生等流转；
- 当前所处状态，以及距离上一关键节点过去了多久。

> 数据可行性说明：现有 CRM 手工快照主要保留当前状态和少量时间字段，历史阶段流转未必完整。后续可通过“定期快照差异”补建未来的流转时间线；历史缺失部分需要盘点 CRM 是否能导出完整日志，不能默认可以补全。

### 3.2 客户健康度与价值判断

基于生命周期、跟进、拜访与订单事实，评估：

- 客户当前价值高低；
- 是否停滞、失联、临近掉保或已经进入躺尸状态；
- 是否需要起死回生、重新分配或更换打法；
- CRM 显示高阶段但 OA 长期无成交的异常；
- OA 已成交但 CRM 阶段未更新的异常；
- 高价值客户缺少实地拜访或持续跟进的风险。

健康度不是单一分数先行，而是先形成可解释的状态与原因；分数可以在状态口径稳定后再做。

### 3.3 主动提醒与管理动作

当客户生命周期出现值得干预的信号时，系统应能主动通知负责人或管理者，例如：

- CRM 高阶段，但 OA 长时间没有订单执行单；
- OA 已有订单执行，但 CRM 阶段未推进；
- 高价值客户长期无跟进、无实地拜访；
- 快掉保、已掉保但仍有成交机会，需要起死回生；
- 代理商订单涉及终端客户，但终端客户长期缺少服务或回访。

通知的具体接收人、频率和灰度机制复用现有钉钉推送体系另行设计。

### 3.4 外勤结合价值：解释过去 + 指导未来

在客户生命周期之上叠加销售外勤数据：

- 跟进次数、拜访次数、拜访频次与状态变化的关系；
- 成交客户在成交前的拜访/跟进组合；
- 高频跟进但无成交的客户，是客户质量、销售动作还是阶段判断问题；
- 已成交客户成交后的实地服务与复购机会；
- 高阶段客户缺少实地拜访时，给对应负责人或区总形成下一步动作建议。

这部分既要服务复盘和归因，也要服务未来行动，不能只做成静态报表。

## 四、范围草案（不是砍边界）

### 4.1 客户同步

当前可行基线是 **CRM 手工导出 → 系统导入**。需要评估并定义：

- 同步对象：客户、联系人、跟进记录、负责人、客户阶段/状态、公私海、掉保与退回记录、区域、渠道、标签等；
- 同步频率：由业务确定，例如每周、每日或关键节点前手工导入；
- 快照机制：每次导入保留批次与快照时间，页面明确展示数据新鲜度；
- 快照差异：识别新增客户、负责人变化、阶段变化、掉保/回池、状态回退等，形成生命周期事件；
- OA 关联发现：订单或拜访表单中出现但本地 CRM 快照尚不存在的客户，应进入“待同步/待确认”清单，而不是直接丢弃；
- 未来扩展：若 CRM API 成本或权限变化，保留自动同步方案；当前不因 API 不可用而否定需求价值。

### 4.2 客户身份与来源映射

需要建立跨 CRM、OA、外勤的统一客户身份：

- 系统统一的 `customer_id`；
- 客户标准名、别名、归一化名称；
- 来源系统与来源 ID（如 CRM ID、OA 关联 ID）；
- 匹配置信度与确认状态；
- 客户类型与角色：CRM 的客户类型描述客户档案，OA 订单中的“终端客户/代理商”描述本次交易角色，两者要分开保存；
- 手工确认入口：同名、近似名、快照缺失、角色冲突等场景需要可复核。

已有验证表明：OA 关联字段可直接提供 CRM `instanceId`，应优先使用；没有关联 ID 的代理商名称等文本字段，再走名称归一化与人工确认。

### 4.3 生命周期事件模型

生命周期不应只是一张客户当前状态表，还需要事件序列。候选事件包括：

- `customer_created` 客户创建；
- `owner_assigned` / `owner_changed` 负责人变化；
- `stage_changed` 阶段变化；
- `follow_recorded` 跟进记录；
- `visit_completed` 实地拜访；
- `order_submitted` 订单执行发起；
- `contract_confirmed` 合同确认；
- `erp_confirmed` ERP 下推/确认；
- `shipped` / `delivered` 发货/交付；
- `returned_to_pool` 退回公海；
- `revived` 起死回生/重新激活。

具体事件来源、时间与状态口径需在数据盘点后确定。

### 4.4 分析与通知

第一阶段先回答事实问题，再逐步进入判断和推送：

- 客户生命周期时间线；
- 节点停留与转化耗时；
- 跟进、拜访、订单三类动作的组合分析；
- 健康度/风险状态及原因；
- 负责人/区域/公司维度的客户经营视图；
- 需要通知的异常与建议动作。

## 五、典型使用场景

### 管理者

- 查看某区域/负责人名下客户的完整生命周期和健康度；
- 找出“CRM 高阶段但长期无 OA 成交”的客户并要求解释；
- 找出“OA 已成交但 CRM 未更新”的数据不一致；
- 观察高价值客户是否缺少实地拜访和持续跟进。

### 区总/负责人

- 收到需要关注的客户清单及原因；
- 判断一个客户应继续推进、补实地拜访、起死回生，还是放弃；
- 复盘成交客户在成交前的跟进与拜访动作。

### 数据/运营维护者

- 查看 CRM 手工同步的新鲜度、成功率与待确认客户；
- 处理同名客户、快照缺失客户、OA 有而 CRM 快照没有的客户；
- 维护客户别名与来源映射，保证下游订单与拜访分析可信。

## 六、权限与敏感信息

订单执行数据包含联系人、地址、合同附件等敏感信息，当前共识是 **admin 可见全量**，其他角色权限待负责人补充。

客户同步本身还需要单独定义：

- 客户联系方式、成交信息、订单金额/附件分别给谁看；
- 区总是否只能看本区域；
- 销售是否能看他人名下客户；
- CRM 公海/私海与本系统权限是否一致。

权限方案未确定前，不把现有拜访系统的总览口径直接套到客户与订单数据上。

## 七、验收指标

- **同步覆盖**：手工导入的客户、联系人、跟进记录完整入库，批次可追溯；
- **数据新鲜度**：页面可见最近同步时间；超过约定周期未同步有明显提示；
- **身份匹配率**：OA/拜访/CRM 能挂到统一 `customer_id` 的比例；
- **生命周期完整度**：关键节点有状态和时间；缺失节点能解释来源，不静默为空；
- **一致性发现能力**：能识别“高阶段无订单”“有订单但 CRM 未更新”等异常；
- **外勤结合价值**：能按客户回看跟进、拜访、订单的完整组合，并支持导出或推送；
- **权限正确性**：订单与客户敏感字段不出现越权展示。

## 八、阶段建议（实施顺序，不代表最终范围）

**分三阶段实施（2026-10-19 拍板）：**

- **第一阶段（P1）**：统一客户身份、跨源匹配及数据来源可信度——手工导入批次、快照差异、统一客户 ID、来源映射、匹配置信度与待确认清单。对应下方原 1、2 步。
- **第二阶段（P2）**：客户生命周期及经营信号——时间线、节点停留、快照差异事件。对应原 3 步及 4 步中的订单执行接入（OA 作为成交事实准绳）。
- **第三阶段（P2）**：客户健康度及主动提醒——可解释的状态与原因、异常识别、推送动作。对应原 5 步。

> 解阻塞原则：**客户身份统一不应成为所有前端体验优化的硬阻塞条件。** 当前沿用既有匹配逻辑（`splitRealCustomerNames` → `normalizeCustomerName` → `resolveCrmName` 三层）支持有限下钻（PRD-007/PRD-008），但页面必须标识匹配状态（精确/归并/待确认/未匹配）并支持未匹配场景的展示与处理入口。

原细步（保留备查）：

1. **数据盘点与口径定义**：确认 CRM 手工导出能提供哪些生命周期字段；盘点 OA 客户登记、客户状态变更、订单执行模板；定义生命周期节点。
2. **客户同步与身份层**：手工导入批次、快照差异、统一客户 ID、来源映射、待确认清单。
3. **生命周期与健康度视图**：客户时间线、节点停留、健康状态与原因。
4. **订单执行接入**：基于统一客户身份接入两张订单执行表，OA 作为成交事实准绳。
5. **外勤结合分析与主动提醒**：解释历史、发现风险、推送下一步动作。

## 九、依赖与风险

- CRM API 需额外付费，当前只能手工同步；同步频率直接影响生命周期与提醒的新鲜度。
- 手工快照无法天然提供完整历史流转，历史阶段变化可能永远缺失。
- 客户同名、快照滞后、OA 关联 ID 与本地快照不一致，会影响身份匹配。
- OA 中的交易角色与 CRM 客户类型可能不一致：订单内角色以 OA 为准，客户档案类型以 CRM 为准，系统需要同时保留。
- 客户、联系人、订单与附件均涉及敏感信息，权限复杂度高。
- 若未来需要 CRM 回写或客户管理动作，需要另行评估写权限、审计与误操作风险；本 PRD 不提前排除。

## 十、已确认决策

- 成交事实与成交主体以 OA「订单执行」/「【代理商】订单执行」为准。
- 代理商订单必须区分终端客户与代理商，不能用单一客户字段覆盖。
- CRM 阶段在打通 OA 后不再是成交判断的最高优先级依据。
- 客户同步是本需求的上游，不是订单接入的附属技术任务。
- 本 PRD 同时评估 OA×CRM 自身价值，以及叠加销售外勤后的解释与行动价值。
- 当前 CRM 自动 API 同步不可用，手工同步是现实基线。
- **2026-10-19**：分三阶段实施（身份/可信度 → 生命周期/信号 → 健康度/提醒）；身份统一不硬阻塞前端有限下钻，但下钻必须标识匹配状态并支持未匹配场景。

# 项目长期约定（map / 销售外勤行为分析系统）

## 业务周口径（用户明确拍板，2026-09-20）

- **业务周起点固定为 2026-06-01（周一），此后连续 7 天一周排下去，不逐年重置。**
- 代码现状（**与口径不符，待修**）：`backend/src/utils/businessPeriod.ts` 与 `frontend/src/utils/businessPeriod.ts` 的 `getAnchorDate(year)` 取「该日期所在年份的 6 月 1 日」作锚点，等于每年重新起算。
- 后果（已用脚本验证）：2027-06-01 是周二 → 2027 年起周边界漂移为周二~周一，且跨年处出现重叠周（2026-12-28 周 与 2026-12-29 周 重叠 5 天）；`getBusinessWeekNumber` 在 2027-01-01 算出「第 -21 周」，每年 6/1 重置回第 1 周。
- 正确实现：锚点写成常量 2026-06-01 00:00 +08:00，`weekIndex = floor((d - 锚点) / 7天)`，周序号连续递增。
- **改这个窗口期是零成本的**：2026 年内所有日期按新旧算法结果完全相同（2026 年锚点本就是 2026-06-01），存量数据不受影响；差异只在 2026-06-01 之前与 2027-01-01 之后出现。

## 两套时间口径是刻意设计，禁止合并

- 口径 A 自然周（周一~周日）：仅服务报告与调度 —— `scheduler.ts` 周报触发（周日 18:00）、`reportGenerationService.generateWeeklyReports` 默认「本周一~今天」、catchup 补跑窗口、月报自然月。自然周计算内联在 scheduler/reportGenerationService，**不在 businessPeriod.ts**。
- 口径 B 业务周（2026-06-01 锚点）：仅服务分析 —— 异常检测「拜访量不足」按周、风险摘要周维度、驾驶舱周序号、前端 DecisionPage/ConsolePage 的「本周/近两周/近三周」筛选。
- 分界是「报告 vs 分析」，**不是**「前端 vs 后端」。后端 `getLastWeekRange` / `getLastTwoWeeksRange` 等看似自然周的函数名，其实是业务周的别名。
- 历史教训：曾误判这两套为「重复实现」并建议合并，被用户纠正。以后看到两份时间计算代码，先问业务口径再动手。

## 沟通偏好

- 不要对用户直接使用 greenfield、brownfield 这类英文行业术语而不解释。
- 用户熟悉自己的业务，但会依赖助手核实代码与口径是否一致；给结论前先跑数据验证，别凭印象。
